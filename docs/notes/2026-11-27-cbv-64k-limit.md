# S-6: constant buffer views are cut to the host's 64 KiB

The console's constant buffer views reach 4 MiB. A host D3D12 view stops at 4,096 rows of 16 bytes
(65,536 bytes), and creating a larger one is an invalid call: the runtime removes the device
(`DXGI_ERROR_DEVICE_REMOVED`, reason `DXGI_ERROR_INVALID_CALL`, no driver reset in the system log).

`descriptor::constant` now cuts every host constant buffer view to 65,536 bytes, and a fresh
table's upload copies only that much. A translated shader reads constants a row at a time and
cannot address past that limit either, so nothing it could read is cut off; the code is marked
`shortcut:` because a console program that reads further would get zeros. There is no switch: the
old behaviour was an invalid call, not a choice.

## How it was found

RTX 5080 16 GB, NVIDIA 616.56, Ryzen 7 9800X3D, 32 GB, Windows 11 Home 25H2 (build 26200),
5120x1440 at 240 Hz, `base` profile, unattended runs with `scripts/measure-run.ps1` from the same
save (the room after the corridor with the guard), 2026-11-27.

- Runs 1 to 3 (`base`, `texture-keep`, `card-windows`) reached the time limit.
- Runs 4 to 16 all lost the device a few seconds after the world's first frame: with every profile
  and with none, after a reboot, with an empty data folder, with an empty cache folder and every
  shader translated again. Free memory, video memory, the monitor, display adapters and Windows
  Update were checked and changed nothing.
- With the Windows feature Graphics Tools installed and `LEONIDA_D3D12_DEBUG=1`, the debug layer
  reported one error before the removal: a constant buffer view of 2,365,184 bytes, over the
  65,536-byte maximum. The removal followed at once.

## Measured

| Run | Build | End | Usual frame | Card time | Draws |
|---|---|---|---|---|---|
| 1, `base` | `6ee73c9` | time limit | 119 ms | 48.8 ms | 7,031 |
| 4 to 16, any profile | `6ee73c9` | device lost | - | - | - |
| 17, `base` | this change on `4b28ba1` | time limit | 100 ms | 42.3 ms | 4,794 |
| 18, `base` | this change on `4b28ba1` | time limit | 104 ms | 41.6 ms | 5,305 |

Runs 17 and 18 both reached the time limit with no crash report. Their frame figures can't be
compared with run 1: the build is about thirty commits newer and the draw count differs, so no
speed-up is claimed for this change.

## Not measured

- Other cards. Two other NVIDIA testers lost the device with `base`, and neither is known to be
  this call:
  - RTX 3060 12 GB, driver 621.40: the last error is a host command list that did not close with
    `0x8007000E` (out of memory), not an invalid call. Probably memory, not this view.
  - RTX 4060 Ti 8 GB, i5-14400F, driver 621.40, as the robbery turned into the escape: the reason
    reported was `0x887A0004`. In the device-removed line that code belongs to the missing
    breadcrumbs (DRED off), not to the removal; the 5080's line carried it too, followed by the
    invalid call. A guess: the same cause. A run of this change on that card would tell.
- Why runs 1 to 3 never made such a view. A guess: the title makes it only in some situations.
- Whether a console program ever reads constants past 64 KiB, and the frame shots of run 17.
