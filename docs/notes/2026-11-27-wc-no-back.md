# P-3: shader writes into big write-combined copies stay on the card (experimental, off by default)

Ported from [readmet3xt-lab/foxhound](https://github.com/readmet3xt-lab/foxhound), commits 50c15a1
(write-combined title memory, no write-back) and 2f81d0c (the size floor), read and written again in
our own code. foxhound's `VICTORY_WC_BAR` (one copy in card memory the CPU maps) is not ported.

## What it changes

The title asks for some of its memory write-combined: the console's 0x400 protection bit, which
`xmem` drops before the host sees it. That is memory its CPU writes and the GPU reads; reading it
back is uncached on the console, so results the title's CPU reads go to cacheable memory.

After each submission we compare what shaders were declared to write in host copies with two sides
(`LEONIDA_CARD_BUFFERS`, copies of 1 MiB or more by default), fetch the pieces that differ and
merge them into title memory. That is part of the frame line's "copying back", which is about 30
ms of a 140 to 150 ms frame on an RTX 3080 12 GB. foxhound found, on a 4070 SUPER, that about 360
of the 730 MB a frame of compared ranges lie in write-combined memory.

- `xmem`'s `XMemVirtualAlloc` notes, before dropping the bit, whether each reservation or commit
  asked for write-combined memory (`leonida_gpu::title_memory_write_combined`, in
  `crates/leonida-gpu/src/wcback.rs`). A later allocation over the same addresses without the bit
  takes them out again.
- `LEONIDA_WC_NO_BACK=1`: a copy with two sides that lies all in write-combined memory and is at
  least `LEONIDA_WC_NO_BACK_MIN_KB` long (KiB, default 16384, 0 for every copy) gets no write-back:
  no hashes, compare, fetch or merge. What shaders write stays on the card. Refreshes still send
  the pages the title wrote. A copy whose memory is not write-watched keeps its write-back, since
  each of its refreshes sends the whole range up; the lists before the first refresh that finds it
  unwatched still skip it.
- The diagnostics build logs, once a second, how many MB a frame of declared shader writes were not
  copied back. It is an upper bound: every draw or dispatch that binds a range declares it again,
  and the count is taken before repeats are dropped, so it does not compare with the copy-back
  line's bytes. The copy-back line itself shows the saving. A count of 0 can also mean the regions
  were taken out by a commit without the bit (see below).
- `gpu-profiles.json` has no profile for it: on the one card measured it lost the device. To try
  it, add a profile that sets both switches to `gpu-profiles.local.json`, say `wc-no-back`.

## Why the floor

With every write-combined copy left on the card, foxhound's cutscenes went near black: small results
the title reads back came back stale. foxhound counted 3,245 write-combined copies, median 4 KB, 82
of 1 MB or more, 7 of 16 MB or more (largest 90 MB). With a floor the picture came back.

foxhound's launcher uses 1024 KB, and the commit's own default is 0 (every copy). Ours is 16384 KB.
Copies with two sides start at 1 MiB by default (`LEONIDA_CARD_BUFFERS_MIN_MB`), so the floor keeps
the write-back of write-combined copies of 1 to 16 MiB: foxhound's tested 1 MB setting, made
stricter. 1024 is worth a run once 16384 is known to keep the picture here.

## What it risks

- The title's CPU reading what shaders wrote there reads older bytes.
- A 64 KiB page the title writes goes up whole from title memory. With no write-back, what shaders
  wrote in the rest of that page is lost: 16 times as many bytes as with foxhound's 4 KiB pages. The
  byte-exact merge for ranges still in flight (`LEONIDA_LATE_WAIT=2`) does not apply to these
  copies either, since nothing of them is pending.
- Another host copy of the same bytes (a texture placed there) does not see what shaders wrote.
- The title's own `VirtualFree` is not seen by us (TODO P-10). Memory freed and taken again outside
  `xmem` still counts as write-combined until `xmem` gives it out again without the bit.
- The other way round, a commit without the bit inside a write-combined reservation takes that part
  out, where foxhound would keep it. That is safe, but the switch then does nothing there. Whether
  the title commits like that is not known.

## Measured

RTX 3080 12 GB, driver 621.24, Ryzen 7 7800X3D, 2026-11-27, `scripts/measure-run.ps1` on the
diagnostics build: the one run with both switches on (a 16 MB floor) lost the device before the
600th frame of the world. The driver reported errors to the event log twice, the last frame lines
took 514, 1,978 and 1,046 ms, and the diagnostics counter said about 32,370 MB a frame of
declared writes were not copied back (an upper bound, see above). The same build with the switch off
ran its time afterwards (median frame 153.5 ms), so on this card the switch is not safe as it
is; no second run with it was made. A cause is not known: a guess is that this tree has copies
in write-combined memory that the title does read back.

foxhound's figures, 4070 SUPER with DLSS Quality: gameplay 38.3 -> 33.3 ms a frame, cutscene
median 47.3 -> 36.3 ms, p95 205 -> 142 ms, the title's busiest thread 57 -> 47% of a core, all
with a 1 MB floor. With a 16 MB floor they give 35.3 ms and do not say for which scene.

To measure it, run `scripts/measure-run.ps1` with and without `-Profile wc-no-back` (the local
profile above) in the same series folder, twice each. Compare "copying back" and the frame time
in `summary.txt`, check the shots for black or stale parts (cutscenes too), and check that no run
lost the device.
